## 注文の届け方

- お客様の注文送信は東京の `submitCustomerOrderItemsCommandAsia` が本線。一時的な障害のときだけ米国の `submitCustomerOrderItemsCommand` へ、同じ `clientRequestId` で送り直す（二重注文にならない）。
- 注文開始 `startCustomerOrderSessionCommand` と東京の送信の2本だけ `minInstances: 1` で常時待機（2026-08-30）。待ち時間を減らすため。費用は Firebase の目安で月約16米ドル（無料枠の前）。ほかの17本は待機させない。
- 全 Functions は Node.js 22、256MiB、同時処理 80、`maxInstances: 20`。

## 品目の取消（2026-10-21）

- メニュー管理の権限が無いスタッフの取消には、店の共通パスコードが要る。ユーザー様が「店の共通パスコード」を選んだ（権限＋承認方式・全員可は不採用）。
- パスコードは `storeSecrets/{storeId}` にハッシュで置き、画面からは読み書きさせない。照合はサーバーだけ。5回続けて間違えると10分ロック。
- 開発用のブラウザ直接書き込みモード（`VITE_ORDER_COMMAND_RUNTIME=client`）ではこの確認が効かない。本番では使われない。

## 入口（2026-10-22）

- 管理の入口はスタッフ画面に一本化（ユーザー様「この際ひとつでもいいよ」）。`/admin` は古いブックマーク用にスタッフ画面へ案内するだけ。
- Google でログインした店長・オーナーは「管理者」としてスタッフ画面に入る。スタッフの記録（`staffSessions`）は作らない（rules・Functions は店舗管理者として扱う）。スタッフとして使うときは、ログアウトして店舗コードで入る。
- 店舗コードで入るときは、必ず匿名のスタッフ端末として入り直す（管理者のログインを流用しない）。

## 権限の確認はサーバーで（2026-10-22 整理 第4章）

- スタッフの操作（注文・着席・提供済み・取消・席移動・予約案内・会計）は、店長・オーナー（Google ログイン）か、4桁パスを通したスタッフの端末だけ。店舗コードだけの端末は `staff-not-selected`。操作した人の名前はサーバーが決める（画面の申告は使わない）。
- 会計（精算）はスタッフ全員に許す（ユーザー様の選択）。
- 注文・明細・会計（`orders`・`orderItems`・`checks`）は Functions だけが書く。人数分の自動追加は店舗設定だけを読む。
- 4桁パスは `staffSecrets` にハッシュで置き、照合・登録・変更は Functions だけ。5回続けて間違えたら、そのスタッフだけ10分ロック（ユーザー様の選択）。照合済みの印（`verifiedStaffMemberId`）の無い端末の記録は信じない。
- 出し方は 4-A・4-B の2回に分ける（ユーザー様の選択）。
- パスを忘れたスタッフは、店長・オーナー（Google ログイン）が今のパスなしで決め直せる（ロックも解ける）。スタッフ管理の権限を持つスタッフは今のパスが要る（ユーザー様 2026-10-22）。

## 権限とログイン

- 店舗の管理者メールを変えても店舗IDは移さない。`storeAdminEmails/{email}` が既存の `storeId` を指す形にし、古い `stores/{uid}` の持ち方も動かし続ける。
- スタッフ権限の項目が無い既存スタッフは、今までの現場の権限として扱う。メニュー管理・レジ締めなどの強い操作は、明示的にオンにしたときだけ。
- スタッフが同じ店の端末で一度4桁パスを通したら、次からは自動で入れる。スタッフ切り替え・ログアウト・パス変更・権限変更で、この近道は消える。
- `/owner` は固定のスーパー管理者だけ。スーパー管理者は店舗一覧から対象店舗を選び（`ownerActiveStoreId`）、その店のオーナーと同じ管理画面に入れる（2026-06-21）。通常のユーザーが同じ値を触っても無視し、rules は既存の `isSuper()` の範囲から広げない。
