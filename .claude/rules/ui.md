# 画面を扱うときのルール

柱3「店の人がストレスなく使える」と、お客様が迷わず注文できること（AGENTS.md 1章）を画面で守るための原則。
旧資料（`docs/archive/reset-2026-10-21/`）に散らばっていたユーザー様の好みをまとめたもの。

## 1. 端末ごとに、速さを優先する

- スタッフはスマホ、厨房とレジはタブレット、お客様は自分のスマホ。試作も確認もその大きさで行う。
- スタッフ画面は、注文追加や会計確定などの主要操作まで長くスクロールさせない。内容は内容の領域でスクロールさせ、主要操作は見失わない位置に固定する。
- レジの預かり金ボタンは、ちょうどの金額を 1000・5000・10000 円より先に置く。同じ金額のボタンを2つ出さない。
- 商品の登録・修正は、少ない手順で迷わずできること。

## 2. 余計なものを出さない

- 分類（フード／ドリンクなど）は文字ラベルを増やすより、枠の色など控えめな見た目の差で表す。
- 使う頻度が低い機能や危険な操作は、常に表に出さず管理画面の奥へ。追加した機能をすべて表に出す必要はない。
- お客様画面のカート・注文履歴・会計依頼は、ほかのアプリと同じ感覚で意味が分かる名前にする。注文前のカート周りでは料金を強く出さず、会計の確認で注文済みの内容と金額を見せる。

## 3. 見た目の方向（ユーザー様 2026-10-22）

- 今の見た目は「全体的に古くさい」。目指すのは**すっきり明るい**形：白と薄いグレーが基本、色は大事な操作だけ、角は控えめに丸く。**余白は少なめ**（ユーザー様 2026-10-22。1画面に多く見せる。ただし押す所は指で確実に押せる大きさを保つ）。
- 黒い帯・細い線だけのボタン・画面ごとに違うグレーはやめる。
- 画面を実装し直すときは、動きだけでなく見た目もこの方向で作り直す（「あとで見た目を直す」にしない）。
- **既存の仕組みや画面があっても、今の方針に沿う構造へ変えた方がよいなら、そちらを優先する**（ユーザー様 2026-10-22）。今の形を残すこと自体を理由にしない（データ・注文の流れを止めない段取りは守る）。
- **作り直すのは色や角丸だけではない。配置と構造から見直す**（ユーザー様 2026-10-22「フォントと少しスクエア系になっただけ。配置とか構造とか適切に変えてほしい」）。画面ごとに「この画面は何のためか・一番上に何を置くか・どの順で並べるか・どこを押すか」を考え直し、今の並びをなぞらない。案は試作の画像で見せて決める。
- 色・角の丸み・影は `src/styles/tokens.css` の共通の値だけを使う。CSS に色を直接書かない（今は53ファイルに直接書かれているので、触った画面から順に置き換える）。

## 4. 見た目の決まり

- 文字は `src/styles/tokens.css` の `--font-main`（M PLUS Rounded 1c）。ラベルとボタンは太字、合計など大事な数字は太さ 900 と等幅数字（`--font-number`）。
- `style={{ ... }}` の直書きはしない（見た目は CSS のクラスで）。
- ブラウザ標準の `prompt` / `alert` / `confirm` は使わず、既存のモーダル・トグルを使う。
- この章の3つ（`style` の直書き・ブラウザ標準の確認窓・色の直書き）は `npm run check:ui-rules` が自動で止める。今ある違反は `scripts/ui-rules-baseline.json` に記録済みで、新しいファイルは0件、今あるファイルは増やせない（ユーザー様 2026-10-22）。直して減ったら `npm run check:ui-rules -- --update-baseline`。基準を増やす方向に書き換えない。

## 5. 表示だけ直す近道をしない

- 厨房の誤操作の取り消しなど、データが変わる操作は Functions のコマンドで安全に戻せる場合だけ作る。表示だけ戻す実装はしない。
- 新しい表示設定は店舗ごとの設定で切り替えられるようにし、設定が無い既存の店は今までと同じ表示にする。

## 6. 見せる前の点検（毎回。過去にユーザー様に直された点）

試作・実装を見せる前に、次を自分で確かめてから出す。直された点が増えたら、ここに足す。
- 配置と構造から考え直したか（色・フォント・角丸だけの変更になっていないか）。
- 余白が多すぎないか。1画面で必要な情報が見えるか。
- 「すっきり明るい」か（黒い帯・画面ごとに違うグレー・古くさい見た目が残っていないか）。
- 主要操作が固定位置にあり、長くスクロールさせないか。頻度の低い操作が表に出ていないか。
- 文言はすべて日本語か。試作は画像にして送ったか（ブラウザの枠はユーザー様から見えない）。
