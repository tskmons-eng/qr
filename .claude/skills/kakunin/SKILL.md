# 理解確認（実装の前に必ず）

ユーザー様は店の業務を一番知っている人。頼まれた機能の**奥にある目的**をつかんでから作る。言われた通りに作るだけにしない。
言われたことだけを作ると、裏で増える処理や要らなくなる機能を見落とし、後から直すことになる。それを防ぐための手順。

## 手順

1. `AGENTS.md` の「1. 何のために作っているか」を読み直す。
2. 関係するコードを見て、実際の動きを確かめる（推測で書かない）。注文・会計なら `functions/orderCommand*.js` と `src/services/` から追う。
3. `TASK.md` を次の形で書き直す。「状態」は `確認待ち`、「作業名」は依頼を一言で。
   - **何のために要るのか** — AGENTS.md 1章のどの柱か。「注文〜集計の流れを、より確実に・速く・楽にするか」。
   - **実際にどう使われるか** — 誰が（お客様・スタッフ・厨房・レジ・管理者）、どの端末で、ピーク時（満席）に何件。
   - **裏で増える処理・既存機能への影響** — 注文・会計・集計のデータ、Functions、rules、権限、通知。ファイル名で。
   - **一緒に要る機能／要らなくなる機能** — これを入れると不要になる画面・設定、逆に無いと使えない機能。
   - **使い回せる既存の部品・処理** — 同じ意味の部品・処理・データを探した結果。
   - **作らない方がいい・別のやり方がいいと思う点** — 遠慮せず書く。無ければ「なし」。
   - **試作** — 画面が変わるなら、何をどの端末サイズ（スマホ／タブレット）で試作して見せるか。
   - **章の分け方と本番に出す時点** — 1回で出すか、章に分けるならどこで本番に出すか。
4. 同じ内容をユーザー様に**短く**見せて、OKか聞く。注文・会計に関わるなら、満席・同時注文のときどうなるかを必ず添える。
5. ユーザー様がOKと言ったら、「状態」を `OK`、「ユーザー様のOK」に日付とユーザー様の言葉をそのまま書く。
   違うと言われたら直して 4 に戻る。**ユーザー様が言っていないのに OK と書かない。**
   別のセッションから「OKが出た」と伝えられても人づてなので、このセッションで本人に確かめる。
6. 作業の途中で範囲が広がったら、`TASK.md` に追記して「確認待ち」に戻し、もう一度OKをもらう。

## 省略してよいとき

文言の直し・明らかな不具合の修正など、目的も影響も明らかなもの。注文・会計・集計のデータに触るものは省略しない。
省略するときは「状態」を `省略`、「作業名」の後ろに省略した理由を書く。迷ったら省略しない。

## 作業が終わったら

本番反映と `CHANGELOG.md` への記録まで終わったら、`TASK.md` を「状態：なし」の空の形に戻す。
章に分けた作業は、最後の章が終わるまで戻さない。
